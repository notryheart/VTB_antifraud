## 2. Что мешало подключению

В рабочем `getter.py` адрес читался из переменной окружения `DATABASE_URL`, затем передавался в `psycopg.connect()`.

Работающий сервер PostgreSQL был доступен по адресу `localhost:5432`. Нужные роль и база — `postgres` и `VTB_mvp`. Но запущенному Python не был доступен пароль этой роли.

Когда ты вводишь пароль в команде `psql ... -W`, его получает только этот запуск `psql`. Сам по себе такой ввод не настраивает пароль для Python API.

Дополнительно в первых попытках подключения были неверные параметры:

- В `postgresql://postgres:5432/antifraud` слово `postgres` занимало место имени сервера. Для указания пользователя нужен разделитель `@`.
- Имя пользователя macOS `yaroslav` не означает, что такая же роль и пароль подходят для PostgreSQL.
- В рабочей базе проекта использовалось имя `VTB_mvp`; `antifraud` в инструкции было примером.

Я добавил общее место настройки соединения и локальный способ ввода и сохранения пароля для Python.

## 4. Как теперь проходит запрос

```text
HTTP POST /assess-transfer
          |
          v
getter.py: TransferRequest проверяет JSON
          |
          v
database.py: connect_database() открывает соединение
          |
          v
getter.py: INSERT INTO transactions ... RETURNING ...
          |
          v
COMMIT: PostgreSQL фиксирует запись
          |
          v
Соединение закрывается, API возвращает 201 и сохранённую заявку
```

`check_db.py` запускается отдельно из терминала. При обычном запросе API этот файл не выполняется. Общая часть у него и API — функции из `database.py`.

Если запрос или фиксация завершаются ошибкой, успешный ответ `201` не отправляется.

## 5. Изменения в getter.py

### Общее подключение к базе

Раньше обработчик сам читал `DATABASE_URL` и открывал соединение:

```python
database_url = os.environ.get("DATABASE_URL")
# Далее проверка наличия настройки и psycopg.connect(...).
```

Теперь внутри обработчика используется:

```python
with connect_database() as connection:
    with connection.cursor() as cursor:
        # Существующий INSERT и получение результата.
```

Настройки соединения находятся в одном месте. Это позволяет команде проверки и API использовать одну базу, одинаковый пароль и одинаковые правила закрытия соединения.

Сам параметризованный `INSERT`, возвращаемые поля и порядок «сначала COMMIT, затем `201`» уже были в рабочей реализации и сохранены.

### Строгие целые числа

Для `sender_account_id`, `receiver_account_id` и `amount` я добавил `strict=True`:

```python
amount: int = Field(strict=True, gt=0, le=2**63 - 1)
```

Теперь JSON-число `15000` принимается, а строка `"15000"` и логическое значение `true` отклоняются с `422`. Это убирает неявное преобразование таких значений в целые числа. Проверки положительности и верхней границы уже существовали.

### Новый адрес GET /health/db

[database_health()](/Users/yaroslav/Documents/GitHub/VTB_antifraud/.delta/worktrees/z1ctzk55q4mp/VTB_antifraud/getter.py:27) вызывает проверку настоящей базы.

- Если подключение, доступ к нужным столбцам и проверяемые права исправны: `200 {"status":"ok"}`.
- При ошибке конфигурации, соединения, схемы или прав: `503`.

Этот запрос не создаёт пользователей, счета или переводы. Пустая `accounts` сама по себе не мешает ответу `200`: работоспособность базы и наличие счетов для конкретного перевода — разные проверки.

### Обработка ошибок

| Ситуация | Текущее поведение | Что изменилось во время аудита |
| --- | --- | --- |
| Неверный JSON, тип или значение поля | `422` до обращения к БД | Добавлена строгая проверка целых чисел. |
| Не задан `DATABASE_URL` | `503`, `Database is not configured` | Проверка перенесена в общий модуль. |
| Счёт отправителя или получателя не существует | `422`, `Sender or receiver account does not exist` | Прежняя обработка сохранена. |

| Другие ошибки PostgreSQL, например отсутствующая таблица | `503`, `Database schema or permissions are not ready` | Добавлен общий обработчик `psycopg.Error`; раньше такая ошибка могла стать необработанным `500`. |

В журнал выводится подготовленное объяснение из `explain_database_error()`, а не полный адрес подключения или пароль.

## 6. Что делает новый database.py

### Загрузка .env

При импорте модуля выполняется:

```python
load_dotenv(PROJECT_DIR / ".env", override=False)
```

`PROJECT_DIR` вычисляется по расположению `database.py`. Поэтому файл настроек ищется рядом с кодом проекта.

`override=False` означает: если терминал уже передал процессу `DATABASE_URL`, значение из `.env` его не заменяет. Это полезно для явных настроек запуска, но старый неправильный `export DATABASE_URL=...` тоже продолжит действовать. Для перехода на `.env` нужно убрать такую переменную и перезапустить API.

`.env` читается при загрузке модуля. Уже запущенный процесс не перечитывает этот файл перед каждым запросом.

### get_database_url()

[Функция](/Users/yaroslav/Documents/GitHub/VTB_antifraud/.delta/worktrees/z1ctzk55q4mp/VTB_antifraud/database.py:39) получает адрес из окружения, убирает пробелы по краям и сообщает об отсутствующей настройке через `DatabaseConfigurationError`.

### connect_database()

[Функция](/Users/yaroslav/Documents/GitHub/VTB_antifraud/.delta/worktrees/z1ctzk55q4mp/VTB_antifraud/database.py:47) управляет соединением:

1. Получает `DATABASE_URL`.
2. Задаёт тайм-аут подключения в пять секунд и получение строк в виде словарей. Эти параметры использовались и раньше, теперь они перенесены из обработчика.
3. Если есть `.pgpass` проекта и не указан другой файл через `PGPASSFILE` или адрес подключения, передаёт его путь в Psycopg параметром `passfile`.
4. Открывает соединение и отдаёт его коду внутри `with`.
5. При нормальном выходе контекст Psycopg фиксирует транзакцию; при ошибке внутри блока откатывает её.
6. В `finally` гарантированно закрывает соединение, включая случай ошибки при самом COMMIT.

Последний пункт появился после реального теста: при отложенной ошибке внешнего ключа COMMIT завершался неуспешно, и прежний вариант оставлял соединение открытым.

### inspect_database()

[Функция](/Users/yaroslav/Documents/GitHub/VTB_antifraud/.delta/worktrees/z1ctzk55q4mp/VTB_antifraud/database.py:64) запускает транзакцию только для чтения и проверяет:

- имя подключённого пользователя, базы и текущей схемы;
- доступность ожидаемых столбцов в пяти таблицах: `users`, `accounts`, `transactions`, `risk_assessments`, `fraud_labels`;
- право `INSERT` в `transactions`;
- права на последовательность ID, если используется обычная последовательность, а не identity-столбец;
- наличие хотя бы одного счёта в `accounts`.

Запросы `SELECT ... LIMIT 0` проверяют, что таблицы и столбцы доступны, без чтения их содержимого.

**Граница этой проверки:** функция не сравнивает автоматически все типы столбцов, внешние ключи и CHECK-ограничения с `mainDB.sql`. Их я отдельно сверил во время аудита. Эта функция также не применяет SQL-схему и не создаёт недостающие таблицы.

## 7. Что делает новый check_db.py

### Обычный запуск

```sh
python check_db.py
```

Команда использует тот же модуль `database.py`, что и API. Она проверяет реальное соединение, печатает базу, роль, схему и результат проверки таблиц и прав.

При успехе возвращается код завершения `0`, при обрабатываемой ошибке — `1`. Пустая `accounts` сопровождается предупреждением и не считается ошибкой подключения.

### Первоначальная настройка пароля

```sh
python check_db.py --setup
```

Последовательность действий:

1. Показывает, к какой базе и роли будет выполняться вход.
2. Запрашивает существующий пароль PostgreSQL через `getpass`: символы ввода скрыты.
3. Проверяет соединение и схему с введённым паролем.
4. После успеха записывает пароль в `.pgpass` этой рабочей копии проекта.
5. Повторяет проверку уже с обычными настройками, чтобы убедиться, что сохранённый пароль используется.

Команда не меняет пароль роли PostgreSQL и не извлекает его из pgAdmin.

Если заданы `PGPASSWORD`, `PGPASSFILE` или пароль прямо в адресе, режим `--setup` просит сначала убрать эти настройки: они могут переопределять файл проекта.

### Как записывается .pgpass

Структура строки файла:

```text
host:port:database:user:password
```

Реальное содержимое файла с паролем в документацию не включено.

Двоеточия и обратные косые черты в значениях экранируются. Файл сначала создаётся как временный с правами `600`, затем заменяет `.pgpass` целиком. Это файл для одного настроенного подключения; существующие дополнительные строки при повторном `--setup` не сохраняются.

`600` разрешает чтение и запись владельцу файла. **Пароль хранится обычным текстом, шифрование файла я не добавлял.** Ограничения доступа и исключение из Git не являются шифрованием.

Python явно получает путь к этому локальному файлу через `database.py`. Обычный `psql` сам по себе не начнёт искать `.pgpass` в папке проекта. Для него нужно отдельно указать `PGPASSFILE`, как показано в README.

1. Открой `getter.py`: посмотри модель `TransferRequest`, затем `assess_transfer()` и новый `database_health()`.
2. Перейди в `database.py`: сначала прочитай загрузку `.env`, затем `connect_database()` и `inspect_database()`.
3. Открой `check_db.py`: в `main()` видно отличие обычной проверки от `--setup`, в `save_password()` — запись локального файла паролей.
4. Посмотри тест успешной записи в `tests/test_database_integration.py`: он показывает, как проверяется сохранение другим соединением.

Для повторной проверки из этой рабочей папки:

```sh
.venv/bin/python check_db.py
```

Для запуска API:

```sh
.venv/bin/python -m uvicorn getter:app --reload
```

После запуска проверка через HTTP:

```sh
curl -i http://127.0.0.1:8000/health/db
```

Связь Python с PostgreSQL настроена для приёма и сохранения заявки. Подключение будущей антифрод-модели остаётся отдельной частью реализации.
