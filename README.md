# VTB_antifraud
Данный репозиторий создан для участия в хакатоне MoscowCup.

## Что уже работает

`POST /assess-transfer` проверяет формат запроса, записывает заявку в PostgreSQL
со статусом `pending` и возвращает `201` после фиксации записи. Существование
счетов проверяется внешними ключами базы. Деньги не переводятся.

**ML-проверки пока нет:** `ML.py` пустой; модель не загружается, оценка риска
не вычисляется, `risk_assessments` не заполняется. `scikit-learn` для текущего
обработчика не требуется и в `requirements.txt` не входит.

## Запуск Python и подключение базы

Выполняйте команды из той копии проекта, где находятся `getter.py`, `database.py`
и `check_db.py`. Виртуальное окружение `.venv` и пользователь PostgreSQL —
независимые вещи: активация Python не настраивает вход в базу.

1. Активируйте существующее окружение и установите зависимости. Для `.venv`:

   ```sh
   source .venv/bin/activate
   python -m pip install -r requirements.txt
   ```

   Если используете другое окружение, активируйте его вместо `.venv`.
   `python -c "import sys; print(sys.executable)"` показывает выбранный Python.

2. Если `.env` ещё нет, скопируйте `.env.example` в `.env`. В нём задайте адрес
   **той базы, в которой находятся таблицы проекта**:

   ```text
   DATABASE_URL=postgresql://postgres@localhost:5432/VTB_mvp
   ```

   Проверьте значения в pgAdmin: сервер → **Properties → Connection**;
   имя базы смотрите в **Databases**. `VTB_mvp` — имя текущей локальной базы,
   на другом компьютере оно может отличаться. Пользователь после `//` и перед
   `@` — роль PostgreSQL. Имя учётной записи macOS само по себе не даёт доступа.

   API и проверка автоматически читают `.env` рядом с `database.py`, независимо
   от текущей папки. Уже заданная переменная окружения `DATABASE_URL` имеет
   приоритет. Если в терминале остался неправильный адрес, выполните
   `unset DATABASE_URL`, чтобы использовался `.env`.

3. Один раз настройте пароль локально:

   ```sh
   python check_db.py --setup
   ```

   Введите существующий пароль роли PostgreSQL, указанной в адресе. Команда
   проверяет реальное подключение, нужные столбцы пяти таблиц и права на запись.
   После успешной проверки пароль сохраняется в `.pgpass` **этой копии проекта**
   с правами `600`. `.env` и `.pgpass` исключены из Git. Пароль macOS и master
   password pgAdmin не заменяют пароль роли PostgreSQL.

   `PGPASSWORD`, `PGPASSFILE` и пароль непосредственно в адресе могут переопределять
   файл проекта. Перед `--setup` уберите такие настройки, если они заданы.

4. Повторно проверьте вход уже без ввода пароля:

   ```sh
   python check_db.py
   ```

   Ожидается `OK: Python подключился к PostgreSQL`. Если таблицы отсутствуют,
   сначала проверьте имя базы. `mainDB.sql` применяют один раз к новой пустой
   базе; повторно выполнять его для существующих таблиц не нужно.

5. Запустите API:

   ```sh
   python -m uvicorn getter:app --reload
   ```

   В другом терминале проверьте соединение и схему через сам API:

   ```sh
   curl -i http://127.0.0.1:8000/health/db
   ```

   Исправная база возвращает `200` и `{"status":"ok"}`. Проверка не создаёт
   записей. При проблеме возвращается `503`, а причина выводится в терминале API.

## Проверка сохранения заявки

Отправитель и получатель должны существовать в `accounts`. Пустая таблица
счетов означает, что перевод с ID `1` и `2` будет отклонён с `422`.

Если вам нужны демонстрационные счета, выполните в нужной базе pgAdmin:

```sql
WITH demo_users AS (
    INSERT INTO users (created_at) VALUES (DEFAULT), (DEFAULT)
    RETURNING id
)
INSERT INTO accounts (user_id) SELECT id FROM demo_users
RETURNING id, user_id;
```

Подставьте **возвращённые ID счетов** в запрос. Например, если это `1` и `2`:

```sh
curl -i http://127.0.0.1:8000/assess-transfer \
  -H 'Content-Type: application/json' \
  -d '{"sender_account_id":1,"receiver_account_id":2,"amount":15000,"currency":"RUB"}'
```

Ответ `201` содержит `message` и `transfer`, включая присвоенный базой `id`
и `status: "pending"`. Сумма — положительное целое число без пересчёта единиц.
Неверные данные и отсутствующие счета дают `422`; проблемы подключения,
схемы или прав — `503`. Повторный запрос создаёт новую заявку:
идемпотентность пока не реализована.

Проверьте результат в pgAdmin:

```sql
SELECT * FROM transactions ORDER BY id DESC LIMIT 10;
```

Для `psql` файл паролей проекта нужно указать отдельно, например:

```sh
PGPASSFILE="$PWD/.pgpass" psql 'postgresql://postgres@localhost:5432/VTB_mvp' \
  -c 'SELECT current_user, current_database();'
```

## Тесты

```sh
python -m pip install -r requirements-dev.txt
python -m unittest discover -s tests -v
```

Обычный запуск проверяет обработчик с подменённым соединением.
`tests/test_database_integration.py` дополнительно проверяет настоящий PostgreSQL:
запись и видимость после `201`, откат ошибки внешнего ключа, ошибку при COMMIT,
проверку схемы и общий конфиг API/CLI. Для этих тестов задайте
`TEST_DATABASE_URL`, указывающий на тестовую базу с правом создания схем.
Тесты создают отдельную схему `antifraud_test_<случайный ID>` и удаляют только её;
существующие таблицы не используются. Без этой переменной интеграционные тесты
пропускаются, и это не доказывает исправность реального соединения.

## Планируемая схема работы проекта

Схема ниже описывает планируемую архитектуру, а не уже реализованные возможности
репозитория. Python отвечает за API и оценку риска моделью машинного обучения,
а PostgreSQL хранит пользователей, счета, переводы и результаты проверок.

![Планируемая схема антифрода: проверка отправителя, получателя и контекста перевода; предупреждение о подозрительной операции до подтверждения; затем серверная проверка и выполнение или отмена.](docs/pipeline.svg)

### Как это работает

1. **Создание заявки на перевод.** Пользователь указывает получателя, сумму и
   валюту. API на Python создаёт транзакцию со статусом `pending` — деньги на этом
   этапе ещё не переводятся.
2. **Подготовка признаков.** Из PostgreSQL берётся история, доступная до текущего
   перевода: обычные суммы и частота переводов отправителя, входящие операции
   получателя и предыдущие переводы между этими счетами.
3. **Оценка риска.** ML-модель анализирует все признаки вместе. Сохраняются оценка
   риска, версия модели, время проверки и причины предупреждения, подтверждённые
   данными.
4. **Подтверждение пользователем.** При низком риске показывается обычный экран
   подтверждения. Для подозрительного перевода появляется окно с объяснением:
   можно отменить перевод, проверить реквизиты или продолжить, если правила
   системы это допускают.
5. **Серверная проверка.** Перед выполнением сервер проверяет актуальность оценки
   для получателя и суммы, соблюдение правил системы и отсутствие повторного
   исполнения. При изменении реквизитов или суммы требуется новая оценка.
6. **Сохранение результата.** Записываются статус перевода и реакция пользователя
   на предупреждение. Подтверждённые результаты проверки на мошенничество можно
   позже использовать как метки для обучения. Продолжение после предупреждения
   не доказывает, что перевод безопасен.

### Данные и примечания к реализации

- `users` и `accounts` описывают владельцев счетов. Отправитель и получатель —
  роли, которые ссылаются на одну и ту же таблицу `accounts`.
- `transactions` хранит заявки на перевод и статусы их выполнения.
- `risk_assessments` хранит результаты модели, а `fraud_labels` —
  подтверждённые метки мошенничества отдельно от прогнозов.
- Для причин предупреждений и ответов пользователей нужно предусмотреть
  дополнительное хранение: в ранее обсуждавшейся базовой схеме этих полей нет.
- Чем выше оценка, тем выше предполагаемый риск. Однако оценка не обязательно
  является откалиброванной вероятностью мошенничества.
